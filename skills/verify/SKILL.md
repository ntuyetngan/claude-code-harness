---
name: verify
description: Run the suites this session's diff requires as one background task and write one receipt per suite so the stop gate and /handoff can trust the result. Prints a GREEN/RED table and a "could not verify" list. Runs by itself once implementation of an approved plan is done, and inside /audit and /handoff; also by hand as "/verify", or "/verify --pest 'tests/Feature/FooTest.php'" to name the tests yourself.
argument-hint: "[--pest 'paths'] [--only phpcs,pest] [--all]"
allowed-tools: Bash(~/.claude/hooks/verify.sh *) Bash(timeout * ~/.claude/hooks/verify.sh *)
---

First decide which tests cover the change. Read the diff, find the callers and usages of what changed (grep for the class, method and route names), and list the test files that exercise them: the tests for the changed classes, the tests for their callers, and any test you wrote. That judgment is yours; the script only runs what it is told and proves the result. Then start `~/.claude/hooks/verify.sh --pest '<those test files>' $ARGUMENTS` from the repo root **as a background task** (`run_in_background: true`): the Bash tool caps a foreground call at 10 minutes and the pest run alone takes longer. Wait for its completion notification; do not poll and do not start a second run meanwhile. When the work follows an approved plan and this is the first verify of the implementation, dispatch the `reviewer` agent right after starting the run, with the brief /audit's step 2 describes (the diff, the plan path, the docs pages, the JSON block); its findings then arrive with the receipts, and /audit uses them instead of a fresh dispatch. The stop gate knows a run is in progress and lets a turn end while it runs. Only when you truly cannot name any test does the script's fallback apply: tests whose file name contains the changed class name, and RED when even that finds nothing. When the run completes, read the tail of its output file and show the table it prints, unchanged. Then:

- If every row is GREEN, say so in one line and name the receipt directory.
- If any row is RED, say which suites are RED and why, in one line each, and what would turn them GREEN: fix the code, add the missing test, or run the suite from the environment the row names. Do not retry a RED suite with the same inputs. Do not describe the work as verified.
- If the script says no suite maps to the changed files, say that and list the files, so a change that should have had a test is visible.
- On a re-run after a fix, keep naming the full test list that covers every changed app method, not only the fixed file's test: CRAP scores all of the session's changed methods from the one pest run, and a narrowed list reads as lost coverage (RED).
- If the table names files outside the plan, say so: they are this session's edits the plan does not name, and /handoff will ask about each.

What the script decides on its own: the scope is this session's changes (files that differ from the session-start snapshot; a file already dirty at session start and unchanged since is the owner's own work and is left out; `--all` widens it to every dirty file). PHP files get php-lint, phpcs and phpstan; the lint suites go GREEN when no error sits on a line this diff added, and count the pre-existing errors in the detail. Pest runs the tests you named once, in `pest.shards` shards at the same time (one provisioned parallel test database each); when app classes changed that run collects coverage and the crap suite scores every method the diff touched against `crap.max` in `~/.claude/config/quality.json` from the merged result (RED names the method and whether to cover it or split it). The lint group, the frontend group and the test group run concurrently, so the wall time is the test group's. A suite whose inputs are byte-identical to an earlier GREEN receipt is reused from it (`--fresh` forces every suite to run), so a small fix after an audit re-runs only what it touched. Config changes get an artisan boot check; frontend files get vitest on their specs and a full vue-tsc type-check, through Windows node while node_modules is Windows-built. Mutation testing runs through /handoff or /quality mutation. Never run pest, phpstan, phpcs, vitest or vue-tsc by hand outside the script, so a receipt is always written.
